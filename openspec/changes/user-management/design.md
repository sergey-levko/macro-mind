## Context

The `users` table is the root entity of MacroMind — every other domain table (foods, meal_logs, nutritional_goals, ai_advice) holds a `user_id` FK. This change introduces the table via Liquibase and exposes a minimal REST surface (register + profile) as a vertical slice following the established controller → service → repository → entity → DTO pattern.

No authentication mechanism is in scope; the user's UUID is the sole identity token for now.

## Goals / Non-Goals

**Goals:**
- Introduce the `users` table via a Liquibase changeset
- Expose `POST /api/v1/users` and `GET /api/v1/users/{id}`
- Establish the `User` entity and repository as the canonical reference for all future FK relationships
- Full test coverage: unit (Mockito) + integration (Testcontainers)

**Non-Goals:**
- Authentication, sessions, or JWT
- `PUT`/`PATCH`/`DELETE` endpoints
- Frontend UI
- Password or credential storage

## Decisions

### 1. Vertical slice under `user/` package

**Decision:** All user-related code lives in `com.macromind.user` — `User`, `UserRepository`, `UserService`, `UserController`, `CreateUserRequest`, `UserResponse`.

**Rationale:** Consistent with the project's vertical-slice convention. Avoids a shared `entity/` package that would couple unrelated slices.

**Alternative considered:** Global `entity/` package — rejected because it creates cross-slice coupling from day one.

---

### 2. UUID primary key generated by PostgreSQL

**Decision:** `id UUID DEFAULT gen_random_uuid() PRIMARY KEY` in the Liquibase changeset; `@GeneratedValue(strategy = GenerationType.UUID)` on the entity.

**Rationale:** UUIDs avoid sequential ID enumeration and align with the domain schema defined in `openspec/config.yaml`. `gen_random_uuid()` is available natively in PostgreSQL 13+ (project uses 16).

---

### 3. `goal_type` as a PostgreSQL ENUM via Liquibase

**Decision:** Create a custom PostgreSQL type `goal_type_enum` with values `LOSE_WEIGHT`, `MAINTAIN_WEIGHT`, `GAIN_MUSCLE` before creating the `users` table. Map to a Java `enum GoalType` annotated with `@Enumerated(EnumType.STRING)`.

**Rationale:** PostgreSQL ENUMs enforce valid values at the DB level. STRING storage survives column reordering and is readable in raw SQL.

**Alternative considered:** `VARCHAR` with a CHECK constraint — simpler to migrate later but loses DB-level type safety.

---

### 4. Email uniqueness enforced at DB + service layer

**Decision:** `UNIQUE` constraint on `users.email` in the Liquibase changeset; service catches `DataIntegrityViolationException` and maps it to `409 Conflict`.

**Rationale:** Belt-and-suspenders: DB constraint is the truth; service layer gives a clean API error rather than a raw 500.

---

### 5. No Spring AI integration in this slice

**Decision:** No Claude API calls in the user management slice.

**Rationale:** AI advice is user-profile-aware but belongs in the `ai-advice` slice, not here. Adding it now would violate slice isolation.

## Risks / Trade-offs

- **PostgreSQL ENUM migration pain** → Adding new `goal_type` values later requires an `ALTER TYPE` DDL statement (non-transactional in some Postgres versions). Mitigation: document the migration pattern in a future `goal-type-extension` changeset if needed.
- **No auth yet** → Any caller knowing a UUID can read any profile. Acceptable for local dev; must be addressed before any public deployment.
- **Email as unique identifier** → Email changes require a future migration. Acceptable scope for this change.

## Migration Plan

1. Run `docker compose up -d` to ensure PostgreSQL is available
2. `./mvnw spring-boot:run` — Liquibase applies `0002-users.yaml` automatically on startup
3. Rollback: Liquibase `rollbackCount 1` drops the `users` table and the `goal_type_enum` type
